Chapter 7 – Deploying the Code

This chapter explains how modern organizations deploy software to servers, why many deployment tools exist, and how systems like Puppet, Ansible, Salt, Docker help automate reliable deployments.

1. Why Are There So Many Deployment Systems?

Deployment is complex because organizations run many applications on many servers with differing requirements and frequent release cycles. Manual installation becomes impossible, leading to the need for automated tools.

  • Large organizations have numerous servers and applications.
  • Each environment (dev, test, prod) requires different configurations.
  • Deployments must be reliable, secure, and repeatable.

2. Typical Enterprise Application Architecture

A common architecture includes:

  • Web Server
  • Application Server
  • Database Server

For small setups, manual deployment works. For large-scale infrastructure, automation tools become essential.

3. Challenges Deployment Tools Must Solve

A. Configuring the Base Operating System

Applications often require a specific OS or certain base packages. Deployment tools help ensure that every machine starts from a consistent and reliable base environment.

Common approaches:

  • Bare-metal/VM installers such as Red Hat Satellite and Cobbler (install a fresh OS and base packages via network boot).
  • Image-based provisioning used in cloud platforms like AWS, Azure, OpenStack (new VMs created from preconfigured images).
  • Container base images such as Docker (define a base image and layer changes on top).

B. Describing Clusters

Deployments must define how groups of machines work together. These cluster descriptions ensure each machine takes on its proper role (web server, database, load balancer, etc.).

  • Puppet, Ansible, and Salt allow defining machine roles and clusters.
  • Docker provides Compose/Swarm for describing multi-container systems.
  • Cloud platforms like AWS offer templates for multi-VM deployments.

C. Delivering Packages to a System

Most applications can be delivered as package files, such as RPMs or .deb files. These packages:

  • Provide versioning
  • Include integrity checks (checksums)
  • Make installation reproducible and predictable

Delivery is usually done via OS package managers (yum, apt), but configuration tools can also deploy packages and files directly.

D. Managing Configuration Files

Applications require different configuration files depending on the environment (test vs production). Therefore, tools must generate configuration files dynamically using templates.

Common configuration file formats:

  • XML
  • YAML (YML)
  • JSON
  • INI / TOML

Templates allow placeholders that get replaced during deployment with values specific to the target machine. This simplifies handling configuration changes across many environments.

Other methods (less preferred) include storing configuration in databases or using CLI APIs, but these reduce flexibility and complicate declarative configuration models.

Virtualization Stacks

Organizations with internal server farms widely use virtualization to isolate components of their applications. Virtualization provides virtual machines (VMs) that simulate hardware such as CPUs and network cards.

Virtualization can also emulate entirely different hardware architectures. For example, tools like QEMU allow developers to emulate mobile devices. Emulation works more efficiently when the host and target architectures are similar (e.g., x86_64 host emulating x86_64 Android).

In server environments, the goal is usually isolation—not full hardware emulation. Virtual machines help limit resource consumption issues by allocating dedicated CPU cores, memory, and other resources per VM.

Containers offer similar isolation but do not emulate hardware. They share the host OS kernel, making them lightweight and suitable for most server applications.

Hypervisors

Hypervisors abstract and manage hardware for VMs. They come in two main types:

  • Bare-metal hypervisors – run directly on hardware (e.g., VMware ESXi).
  • Hosted hypervisors – run inside an existing OS (e.g., KVM on Linux).

Common virtualization technologies include:

  • VMware ESXi – proprietary, widely used in enterprises.
  • KVM – open source, cost-effective for large deployments.
  • Xen – supports paravirtualization for improved efficiency.
  • VirtualBox – open source, popular among developers for local OS emulation.

Many hypervisors expose APIs for automation. The libvirt API supports managing KVM, QEMU, Xen, LXC, and others.

Executing Code on the Client

Configuration management systems often allow administrators to execute commands directly on selected nodes based on their roles. This is useful for tasks such as debugging or bulk maintenance.

Introduction to Automation and Ansible

Automation is one of the defining techniques of DevOps engineers, and it's not without reason. Both developers and operators have long used automation to provide services—operators automate server configuration, while developers automate build processes.

Historically, tools such as CFEngine allowed administrators for the first time to define system state using a Domain Specific Language (DSL). Since then, configuration management tools have grown rapidly. Among the top tools used today are CFEngine, Chef, Puppet, Salt, and Ansible.

Ansible has gained huge popularity due to its simplicity—using YAML syntax, agentless architecture, and low learning curve. This makes Ansible ideal for beginners and experts alike.

Ansible Automation Demo – Install Nginx & Deploy Website

Folder Structure

ansible-demo/
├── inventory.ini
├── nginx-local.yml
└── website/
    └── index.html

inventory.ini

[local]
localhost ansible_connection=local

website/index.html

Website deployed using Ansible on localhost!

nginx-local.yml (Playbook)

---
- name: Install Nginx and deploy website on localhost
  hosts: local
  become: yes

  tasks:
    - name: Install Nginx
      apt:
        name: nginx
        state: present
        update_cache: yes

    - name: Start and enable Nginx
      service:
        name: nginx
        state: started
        enabled: yes

    - name: Deploy website folder
      copy:
        src: website/
        dest: /var/www/html/
        owner: www-data
        group: www-data
        mode: '0644'

Run the Playbook

$ ansible-playbook -i inventory.ini nginx-local.yml --ask-become-pass

Test Website

http://localhost

You should now see your deployed HTML page via Nginx!

Advantages of Using Ansible

  • Simple, human-readable YAML — anyone can learn it quickly.
  • Agentless architecture — no agents required on managed nodes.
  • Idempotent — safe to run repeatedly without breaking anything.
  • Fast setup — install and use immediately.
  • Reusable playbooks — automate once, use everywhere.
  • Supports cloud, servers, containers, and network devices.
  • Ideal for CI/CD pipelines.

Conclusion

With just a few files and simple commands, Ansible can automate server setup, install Nginx, and deploy your website. Its simplicity and power make it one of the most valuable tools for DevOps professionals.

Why Use Ansible for Multi-Server Automation?

  • Agentless – Uses SSH, no additional software required on servers.
  • Fast deployment – Push configuration to 1, 10, or 100 servers easily.
  • Consistent automation – All servers get identical configuration.
  • Idempotent – Running again won’t break anything.
  • Simple YAML playbooks – Easy to read, write, and maintain.
  • Scalable – Add new servers to inventory and run playbook again.

Conclusion

Ansible makes it extremely easy to deploy software like Nginx and distribute web applications across multiple servers. With a simple inventory file and a small YAML playbook, you can automate deployments that would normally take hours—reducing errors and saving time.

Puppet Master and Puppet Agents

Puppet is a widely used deployment and configuration management system, especially in large organizations. It uses a client–server model where Puppet agents (clients) periodically contact the Puppet master (server) to check for configuration updates.

How Puppet Works

  1. The Puppet agent initiates communication with the Puppet master to check for updates. This communication is typically secured using SSL.
  2. The agent sends its credentials so the master can identify which node is requesting updates.
  3. The Puppet master compiles the node's configuration into a Puppet catalogue, based on:
    • Role-based configurations
    • Node-specific configurations
    • Inherited roles and modules
  4. The agent applies the received configuration locally to match the desired state.

Puppet follows a declarative approach: administrators describe the desired state of a system, and Puppet determines how to enforce it.

Pros of Puppet

  • A large community with extensive documentation and ready-made modules.
  • Many reusable modules for common software deployments.

Cons of Puppet

  • Puppet agents require several dependencies, including a Ruby runtime that may not match older enterprise OS versions.
  • Puppet configurations can be complex to write, debug, and test.

Example: Deploying Nginx Using Puppet

Step 1 — Create Puppet Manifest

Create a file named site.pp with the following content:


# site.pp
node default {

  # Install nginx
  package { 'nginx':
    ensure => installed,
  }

  # Ensure service is running
  service { 'nginx':
    ensure     => running,
    enable     => true,
    require    => Package['nginx'],
  }

  # Deploy website folder
  file { '/var/www/html/':
    ensure => directory,
    owner  => 'www-data',
    group  => 'www-data',
    mode   => '0755',
  }

  file { '/var/www/html/index.html':
    ensure  => file,
    content => "<h1>Website deployed on localhost using Puppet!</h1>\n",
    owner   => 'www-data',
    group   => 'www-data',
    mode    => '0644',
  }
}

Step 2 — Apply Manifest Locally

Run the following command:

sudo puppet apply site.pp

Result

Puppet will install nginx, ensure the service is running, and deploy the index.html file — similar to the behavior of your Ansible playbook.

SaltStack

SaltStack, commonly known as Salt, is a fast and scalable configuration management and remote execution tool. It allows administrators to define the desired state of systems using declarative configuration files called Salt States. Salt can manage large server farms efficiently due to its event-driven and high-speed communication system.

Salt typically uses a master–minion architecture, where the Salt Master orchestrates and controls configuration, while Minions execute those configurations. For smaller setups or testing, Salt also supports a masterless mode using: salt-call --local.

Key Advantages

  • Fast execution using event-driven architecture.
  • Flexible — supports both master/minion and masterless modes.
  • Simple YAML-based state files.
  • Large community and many built-in modules.

Challenges

  • Salt Master setup can be complex for beginners.
  • ZeroMQ communication may require additional configuration.
  • Learning pillars, grains, and state system takes time.

SaltStack provides a powerful and efficient way to automate configuration and software deployment, similar to Puppet and Chef, but often faster and more flexible in execution.

Chef: Configuration Management System

Chef is another popular configuration management and infrastructure automation tool used in many organizations. Like Puppet, it allows you to define how systems should be configured, but Chef uses a different approach and architecture.

Chef Architecture

Chef follows a client–server model consisting of:

  • Chef Server – Stores cookbooks, roles, environments, and policies.
  • Chef Client – Runs on each node and applies configuration.
  • Workstation – Where developers create cookbooks and upload them to the Chef server.

How Chef Works

  1. The Chef client connects to the Chef server to check for updates.
  2. The node authenticates using its client key.
  3. The Chef server determines which configuration (run list) applies to the node.
  4. The Chef client downloads the necessary cookbooks (recipes, templates, files).
  5. The client executes the recipe instructions to bring the node to its desired state.

Unlike Puppet’s declarative model, Chef uses a more imperative and Ruby-based domain-specific language (DSL) to define configurations.

Chef Concepts

  • Cookbooks – Collections of recipes and resources.
  • Recipes – Define the actual steps to configure software.
  • Resources – Declare actions (install package, create file, start service).
  • Run List – The order of recipes a node must execute.
  • Ohai – A tool that collects system information and sends it to the Chef server.

Pros of Chef

  • Highly flexible due to Ruby-based DSL.
  • Large ecosystem of community cookbooks.
  • Strong integration with cloud platforms such as AWS and Azure.

Cons of Chef

  • Steeper learning curve because configurations are code-heavy.
  • Chef Server setup is more complex than agent-only systems.
  • Testing Chef cookbooks can be time-consuming.

Example Workflow Summary

  1. Create cookbook on workstation.
  2. Upload cookbook to Chef server.
  3. Node checks in → receives cookbook → applies configuration.

Chef Example — Install Nginx & Deploy Website

This example demonstrates how to:

  • ✔ Install Nginx
  • ✔ Deploy a website
  • ✔ Run Chef locally using chef-solo (no Chef Server required)

Folder Structure

chef/
 ├── solo.rb
 ├── runlist.json
 └── cookbooks/
     └── myweb/
         ├── recipes/
         │   └── default.rb
         └── files/default/index.html

Step 1 — Create solo.rb

solo.rb

cookbook_path ["./cookbooks"]

Step 2 — Create Runlist

runlist.json

{
  "run_list": ["recipe[myweb]"]
}

Step 3 — Chef Recipe

cookbooks/myweb/recipes/default.rb

package 'nginx'

service 'nginx' do
  action [:enable, :start]
end

directory '/var/www/html' do
  owner 'www-data'
  group 'www-data'
  mode '0755'
end

cookbook_file '/var/www/html/index.html' do
  source 'index.html'
  owner 'www-data'
  group 'www-data'
  mode '0644'
end

Step 4 — Add Your HTML File

cookbooks/myweb/files/default/index.html

Website deployed on localhost using Chef!

Step 5 — Run Chef Solo

sudo chef-solo -c solo.rb -j runlist.json

✔ Output

Chef installs Nginx and deploys your HTML file successfully on localhost.
